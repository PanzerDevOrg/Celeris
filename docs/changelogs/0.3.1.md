# Changelog: Celeris v0.3.1 (1.21 – 26.3)

Native physics now reaches NeoForge on Java 21 without any launch flag: Celeris tries a JNI binding first, then FFM, then plain Java. It also carries everything 0.3.0 brought (item transport through pipes, listed after the 0.3.1 items) and what was prepared as 0.2.3, so a player coming from 0.2.2 reads one list. Nothing that worked before is taken away.

---

## Key Features & Changes

* **Native Physics Over JNI**: The physics kernel is now also loaded through JNI, which needs no `--enable-preview` and is not blocked by `--enable-native-access` on NeoForge. The engine order is JNI, then FFM, then pure Java; if a native library is missing or fails to load, the next one is used and results stay the same, bit for bit. The kernel and its data layout are unchanged.
* **Nearest3**: A new helper (`core.spatial.Nearest3`) finds the three nearest points of a small set stored in flat int arrays, without allocating. Tested against a plain reference.
* **Quieter Logs**: The JNI memory access no longer prints Unsafe removal warnings.


### Also new since 0.2.2 (0.3.0 and the unpublished 0.2.3)

* **Item Transport**: A new solver moves items along the pipe segments of a network, one tick at a time, with spacing between items, routers that decide where an item goes at a junction (round robin, priority and filter ones are included) and inventories at the ends of the pipes. The result is the same whatever order the pipes are stored in.
* **Items Survive Edits**: Placing or breaking pipes no longer loses the items inside. A mod that asks for it gets each item carried over to the pipe that now covers the same stretch, with the same speed and place; items on a stretch that no longer exists are handed back to the mod instead of vanishing.
* **Saving Networks**: The state of every segment (items in flight included) can be written and read back by position, so a saved world comes back with its items where they were. Files carry a version, and a malformed or too-new file is refused, never half applied.
* **Drawn Without Entities**: A client works out where each item is, every frame, from the last news about it. Servers send a small message only when something changes (an item enters, changes pipe, changes speed or leaves), not positions every tick. Messages are size-capped and checked as a whole before anything is applied.
* **Fast World Loads**: Adding many pipe blocks at once builds the whole network in one pass. 10,000 blocks in a straight line: 9 s → 3 ms; a 100 × 100 grid: 45 ms → 4 ms.
* **Watching a Network**: Mods can be told when pipe segments are created, removed or changed, and can look at the pipes around a block, without scanning the whole network every tick.
* **Fixes**: Changing the connections of a block in the middle of a pipe left an old segment behind. A pipe at position (-1, -1, -1) was mistaken for "no pipe" when a neighbour was removed. The continuous pipe solver copied its segment list and reallocated its scratch space every tick; it no longer does.
* **Checked Positions**: `NodeId.inRange` and `NodeId.packChecked` tell a mod when a position does not fit the packed form (the unchecked form wraps and would alias another block). Vanilla's world and height limits all fit.
* **Big Networks**: Pipes backed up behind a full consumer are no longer walked item by item every tick: 8 million items waiting behind refusing consumers cost 6 ms a tick instead of 29 ms. `TransitSolver.setWorkers` optionally shares the pass over flowing items with worker threads (the same result, bit for bit): 8 million flowing items, 42 ms → 18 ms with 3 workers.
* **Example Mod**: The pipe block of `celeris_example` now carries items: right-click a pipe end with an item, watch it travel, and see it go into a chest at the other end.


### Also new since 0.2.2 (prepared as 0.2.3)

* **Fabric Support**: Every Minecraft version Celeris covers now has a Fabric file as well (needs Fabric Loader 0.16+ and Fabric API). Fabric players can join NeoForge servers that run Celeris, and players without Celeris can join Fabric servers that have it.
* **Native zstd Without Flags**: On Java 21, zstd compression now runs natively out of the box; `--enable-preview` is no longer needed for it.
* **Faster Compression**: zstd reuses its working memory between calls instead of setting it up every time, and network packets are compressed with less copying. Packets on the wire are unchanged.
* **Faster Worker Hand-off**: Results passed from worker threads to the game thread move up to 4× faster when one worker is sending them.
* **Native Physics on NeoForge**: Removed advice to add `--enable-native-access`, which on Java 21 switched the native physics kernel off under NeoForge.
* **Tidier Native Files**: Native libraries are unpacked once into a cache folder and checked, instead of piling up copies in the temporary folder. Windows on ARM and less common Linux CPUs no longer try to load libraries built for other processors.
* **Sturdier Physics Kernel**: Items with impossible positions or speeds (NaN, infinity, teleports billions of blocks away) are left to vanilla instead of being simulated, and the native kernel refuses malformed calls instead of reading or writing outside its buffers. Results for normal items are unchanged, bit for bit, on every CPU.
* **No Stalls on Item Piles**: Looking for touching items in a pile of thousands of items in one block no longer takes tens to hundreds of milliseconds; it stops once it has as many pairs as it can keep (4,096 items: 36 ms → 0.06 ms; 16,384 items: 750 ms → 0.3 ms).
* **Compression Level Setting**: The network compression level can now be changed, from 0 (no compression, least CPU) to 9 (smallest packets); the default, 1, is what Celeris used before. It is in the mod's Config screen on NeoForge and, with Mod Menu, on Fabric (or in `config/celeris.properties`).

## Performance

* Native physics over JNI gives the same results as FFM and plain Java, bit for bit; in a server tick with 100,000 items on the ground the three engines are within noise of each other (about 205 ms), because the work left in the tick is the game's own. JNI's gain is that it works without launch flags.
* 100,000 items on 200-block pipes: 101 µs per tick against 261 µs for one object per item (2.6×). On 20-block pipes with a junction every 20 blocks it is a tie (326 µs against 317 µs): most of the time there is spent handing items over at junctions.
* The vector-based advance of item positions gives the same results as the plain loop and is not measurably faster; the speed-up above comes from the flat layout.
* See [the Benchmarks wiki page](https://github.com/bichal/Celeris/wiki/Benchmarks) for the full tables.
